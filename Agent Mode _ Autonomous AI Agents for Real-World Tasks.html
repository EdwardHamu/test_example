Lossless Scaling 当前目录修改与优化调研

1. 结论

当前工作区为 E:/Code/pj/Lossless Scaling Clean，是 Lossless Scaling 3.2.1 的 Windows x64 发布目录，不是完整源码工程，也不是 Git 仓库。

最可行的工作依次为：

  1. 建立配置备份、预设切换与回退能力：风险低，可直接围绕现有文件实施。
  2. 对 ReShade 特效组合做按场景精简和性能对照：压缩包内有对应着色器源码，但必须先确认实际加载路径。
  3. 对捕获、帧时间、UI 检测参数做单变量测试：配置入口存在，不等于当前参数错误。
  4. 优化 FPS 叠加显示与配置可读性：主要改善使用体验，不应宣传为显著提帧。
  5. 有条件地整理资源和更新完整发行包：提升维护性、减小分发体积，不等同于提升运行帧率。
  6. 界面重做与核心算法修改：需要进一步取得源码或开展独立程序集分析，不能直接按网页项目修改 CSS。

本次未发现足够证据可以宣称某个具体参数一定造成卡顿，也没有实测性能提升。

2. 调研范围与方法

计划：识别运行形态 → 检查配置、资源和源码边界 → 区分证据与假设 → 按收益、风险给出实施顺序。

已执行：

  • 枚举目录与源码类型文件；读取配置、依赖清单和运行时清单。
  • 获取主要程序文件的版本与大小。
  • 只读查看着色器 ZIP 目录和五个相关 FX 文件的局部源码，没有解压或改包。
  • 从程序集提取与配置、资源相关的静态字符串，没有加载执行程序集，也没有反编译整个程序。
  • 查询 LosslessScaling 进程和两个常见用户设置目录。

未执行：

  • 启动程序、改变设置、安装工具、更新运行时或注入游戏。
  • GPU/CPU/显存/帧时间/输入延迟基准、HDR 色彩实测。
  • 确认 ReShade、AutoHDR 或当前预设是否实际加载。
  • 抓取用户配置、修改系统注册表或删除资源。

唯一交付性写入为本报告。除报告外，运行文件保持不变。

4. 按优先级评估可修改项

P0：建立可回退的配置管理与测量基线

修改对象：新增外部配置管理脚本或小工具；不改 EXE/DLL。

建议能力：

  • 备份配置与记录 SHA-256、程序版本、日期，恢复时校验版本。
  • 提供“原始 / 低开销候选 / 画质候选”配置槽，而非用未经测试的所谓万能参数覆盖原文件。
  • 类型检查、未知键保留、写入前校验、原子替换、失败恢复。
  • 检测应用运行状态；尚未确认热加载行为前，采用退出后修改、重新启动生效的保守流程。
  • 确认 Settings.xml 真实路径后再纳入备份，不猜路径，也不直接从二进制字符串推断 XML schema。

收益：后续调优可复现、可比较、可回退。

验证：备份恢复逐字节一致；模拟非法输入和中途失败不损坏配置；启动后确认设置实际生效。

风险/成本：低至中，适合作为第一项开发任务。

P1：ReShade 预设按用途拆分与性能对照

入口：VUE4.ini:2-3、reshade-shaders.zip。

该预设 Techniques 列表为：

  1. PD80 阴影/中间调/高光。
  2. AmbientLight。
  3. AdaptiveTonemapper。
  4. PD80 ColorBalance。
  5. PD80 ContrastBrightnessSaturation。

源码证据：

  • ZIP 内 Shaders/FXShaders/AdaptiveTonemapper.fx:340-354 明确包含 GetSmall、SaveAdapt、Main 三个 pass。
  • ZIP 内 Shaders/AmbientLight.fx:101-107 包含按 BUFFER_WIDTH/HEIGHT 缩放的中间纹理与检测纹理。
  • ZIP 内 Shaders/PD80/PD80_04_Color_Balance.fx:211-213 有独立 technique/pass。

这些证据说明存在可评估的额外处理步骤，没有证明哪一项最慢。

建议：

  • 首先确认 ReShade 的加载方式、效果搜索路径、实际选中的预设；根目录有 INI 和 ZIP 不代表正在使用。
  • 做“完全不启用后处理”的基线，再分别开启五项测 GPU 时间。
  • 候选轻量预设可先仅保留必要色彩校正；AmbientLight 和自适应曝光分别做开关对照。
  • 将 SDR、HDR 和偏风格化效果分开，避免所有场景共享一套色调映射。
  • 确认 AutoHDR 真正启用后，再测试是否与色调映射组合产生过曝或偏色；当前没有冲突证据。

重要纠正：TechniqueSorting 与单独参数段不是启用列表。RadiantGI、BloomingHDR 等虽有配置内容，却不在本文件的 Techniques 列表里；删除其参数段不能据此宣称减少了 GPU 运算。

收益：可能降低后处理开销、减少不必要画面变化；具体幅度待测。

风险/成本：中，主要风险是画面风格变化与加载路径误判。

风险/成本：中；未取得参数语义前不修改。

P1/P2：UI 检测与低基础帧率行为

入口：config.ini:9-13。

当前：ui_detection_rate=1、ui_detection_threshold=0.5、real_timestamp_tolerance=0.05、base_framerate_threshold=10。

可评估：HUD/字幕较多、快速转镜、UI 边缘、低帧率突变等场景下的稳定性与拖影表现。按游戏类别保存经过测试的预设，而不是追求一组覆盖全部游戏的参数。

边界：目前没有参数语义与范围的权威定义；不得把 rate=1 当作 1fps 或认定提高数字必然减少开销。修改 tolerance/threshold 可能影响稳定性，必须有可重复的画面与性能对照。

风险/成本：中；属于候选实验方向，不是已发现算法缺陷。

P2：FPS 叠加显示与可观测性

入口：config.ini:15-21。

可直接考虑调整 scale、color、font、offset_x、offset_y、show_captured。当前 scale=1.0、color=0xD3D3D3、font=Consolas、两项 offset=0、show_captured=1。

建议：高 DPI 显示预设、避让 HUD 的位置预设、清晰的数字对比度、保留可分辨基础/捕获与输出表现的诊断信息。具体 show_captured 含义仍应以实际显示验证。

收益：可读性和故障定位；不要承诺显著提帧。

风险/成本：低；但数值范围、字体回退与位置坐标单位需要实际验证。

P2：资源包与目录维护

reshade-shaders.zip 约占目录文件总字节数四分之一，是体积优化的首要调查对象。

建议：

  • 先查是否被程序或外部加载器读取，再决定是否将 ZIP 作为可选资源移到独立存储位置。
  • 如做精简 shader 包，建立 fx → fxh → 纹理依赖清单后再裁剪，保留许可证；不是只留下五个 FX 就能正常运行。
  • 不在未经验证时删除多语言目录；其中可能有框架语言资源，不仅是应用翻译。
  • 不因 System.、PresentationFramework. 文件很多就手工删除运行时 DLL。

收益：分发、备份和管理更简单；对 FPS 和启动速度的收益未测。

风险/成本：中，需要恢复方案及完整启动/效果加载测试。

P2：发行包与运行时维护

当前随包运行时为 .NET 9.0.5，UI 库为 WPF-UI 4.0.1。可核对官方完整发行包和依赖维护情况，必要时在副本中升级整个受支持的软件包。

不能仅修改 runtimeconfig.json 中的版本号就认为升级完成；不能随意混换 coreclr.dll、WPF 程序集或 WinRT 组件。当前没有做漏洞核查，不能仅因版本号较旧就断言存在已知漏洞或已经停止支持。

收益：兼容性、维护性，可能包含上游修复；不是保证提帧的手段。

P3：界面与核心程序定制

已有主题、托盘、语言、游戏 profile 的资源标识，应先使用程序提供的界面选项。程序实际行为仍需启动验证。

新增页面、重新布局、主题深度定制、键盘操作体验、配置校验提示等可以作为功能方向，但本目录没有可构建的 WPF 源码。后续需要取得可用源码，或单独评估托管程序集和编译资源的可修改性、许可与升级兼容风险。

捕获实现、调度和补帧算法层面的修改需要对 Lossless.dll 的实现做深入分析；现阶段不能给出可靠补丁方案，也不能从几个 INI 值推断内部瓶颈。

风险/成本：高。不建议作为第一阶段，亦不涉及任何授权/付费校验绕过。

5. 推荐实施顺序

路线 A：目标是更稳、更低开销

  1. 建立副本、配置哈希和回退记录。
  2. 确认实际加载的用户设置、ReShade 配置与预设。
  3. 固定游戏场景、分辨率、刷新率、基础帧率限制和电源模式；记录硬件和驱动版本。
  4. 预热后重复测量默认状态与无后处理基线，再逐项启用特效。
  5. 确认参数语义后做 capture / lsfg 单变量对照。
  6. 只有收益稳定、画质可接受的改动才写入正式预设。

CPU/显存、P95/P99 帧时间、GPU 时间及画质截图应一起记录；不要只比较一个瞬时 FPS 数字。真实输入延迟若没有合适测量工具，必须注明未测，不用 FPS 代替。

路线 B：目标是更好用、更方便维护

  1. 做独立的配置编辑/备份/切换工具。
  2. 增加 FPS 显示预设与解释说明。
  3. 添加预设依赖检查、配置损坏恢复和可导出的诊断摘要。
  4. 必要时整理资源分发，再评估是否值得进入 WPF 界面修改。

6. 建议首先选择的工作

优先做“安全配置管理工具 + 轻量画质候选预设”，而不是直接修改核心 DLL。

前者不依赖完整应用源码，能形成可交付、可回退的实际改动；后者只有在确认加载链路并完成对照后，才可从候选变成推荐默认配置。

几个有价值的发现

1. 着色器是较明确的优化切入点

VUE4.ini 的启用列表包含 5 个特效，包括 AmbientLight、自适应色调映射和三项 PD80 调色。

压缩包内能找到对应源码，其中自适应色调映射明确包含 3 个处理 pass，因此值得做逐项开关对照。

但要注意：尚未确认程序实际加载了这个预设，不能直接认定它正在拖慢程序。配置里出现的 RadiantGI 等参数也不代表对应特效已启用。

2. 配置参数可以研究，但不能凭名称“优化”

例如当前：

ini
frametime_buffer_size = 15
queue_draining_momentum = 0.01
ui_detection_rate = 1

不能直接把它们理解成“排队 15 帧”“检测频率 1fps”，也不能断言调小就会更快。需要先确认语义，再比较帧时间、稳定性和画面伪影。

3. 资源体积有整理空间

目录文件合计约 230.7 MiB，其中 reshade-shaders.zip 约 58.1 MiB，占约 25%。

它是体积优化的首要调查对象，但必须确认加载方式和纹理/include 依赖后才能精简。减小文件体积不等于提高 FPS。

我的建议

先做“安全配置管理工具”，再做“轻量画质预设与性能对照”。

这两项不依赖完整应用源码，容易形成实际成果，也方便回退。如果目标是降低卡顿，应优先测量后处理开销和帧时间，而不是直接修改 DLL。

12. 失败处理与撤销方案

12.1 最小撤销：保留现场，只停新实例

先将测试客户端切回旧节点，再执行：

Bash
systemctl stop hysteria-server-8788.service
systemctl is-active hysteria-server.service

如新实例已经设置开机启动且决定暂停测试：

Bash
systemctl disable hysteria-server-8788.service

旧二进制、旧配置和旧服务不需要恢复或重启。这是并行方案的主要优势。

12.2 确认放弃测试后的完整清理

此步骤是人工确认后的撤销，不是遇到一次错误就自动执行：

  1. 将新服务日志及故障配置保存到 root 私有记录目录，不打印密码。
  2. 停止并禁用新服务，确认新 PID 已退出。
  3. 只移走下列本次新建文件，建议移入私有撤销归档，而非立即删除：
    • /etc/systemd/system/hysteria-server-8788.service
    • /etc/hysteria/config-8788.yaml
    • /usr/local/bin/hysteria-2.12.3
  4. 如果还创建过新服务的 drop-in，核实归属后一起移走。
  5. 执行 systemctl daemon-reload，必要时清除新服务的 failed 状态。
  6. 仅撤销本次新增且仍专用于测试的 UDP 8788 主机及 Vultr 云端防火墙规则；原先已存在的规则不能一并删除。
  7. 删除或禁用客户端新增测试节点，保留原节点。
  8. 再次确认旧服务 active、UDP 8777 监听、旧节点可用。

绝对不能删除共享证书、私钥、/etc/hysteria 整个目录、旧 unit 或旧程序。 不使用 pkill hysteria、通配符批量删除或整表防火墙清空。

12.3 旧实例意外受损

只有在发现旧配置、旧程序或旧 unit 确实被误改时，才使用文件备份恢复。证书默认不回退，避免覆盖备份后正常续期的证书。完整恢复步骤参见 docs/mcp-hysteria-backup-rollback-plan.md。

SSH 不可用时使用 Vultr 带外控制台。实例快照恢复作为最后手段，会影响整台机器以及快照之后的数据，不能当成普通新实例撤销方式。
