# 会话完成通知可靠性修复（2026.09.26.9）

## 修复的原因

已用旧代码复现：网络 complete 时 Stop 按钮仍在，但 350ms 轮询没采到生成状态；或者 500ms 防抖回调看到按钮短暂重现而退出，后续没有下降沿。这两种情况都会让已结束轮次不再检查。

另有上下文过早失效：新会话 UUID 稍晚出现、开始时账号待确认，以及后台标签页超过 90 秒使账号校验结果过期。旧 gate 会永久 blocked/done。发送失败则没有重试，no-cors 也无法判断 HTTP 成功。

## 当前行为

- 保留待完成意图，轮询持续重检；后续内容会取消过早的防抖。相同 generation 最多确认一次完成，不新增第二个发送/捕获器。
- Stop 按钮必须可见、可操作，排除 disabled/aria-disabled、会话消息、日志、代码及脚本抽卡面板内按钮。
- 完成后可等待首次 UUID 或账号确认最多 30 秒。账号刷新只使用已有只读 refresh API；必要时复核即将过期/已过期的账号状态。
- 账号 epoch、真实身份、需刷新标记、已绑定会话 URL 或 generation 改变会取消旧轮次。不会无条件删除隔离检查，也不会把旧会话的完成套给新会话。
- 抽卡轮次仍不发送普通完成通知。Thinking Stop 仍使用自己的通知类型，但使用同一稳定事件投递机制，不与普通完成叠加。
- 页面离开取消等待/重试；返回后新的有效轮次仍可工作。

## 新旧服务端兼容

先向固定 `https://meamoe.top/koa/notify2/capabilities` 发只读 GET（2 秒超时，不携带 Cookie/认证）。不发真实通知作能力探测。

- **新服务端**声明 protocol=1、acknowledgements=true、deduplication=true：通过 CORS 可读取响应的 text/plain POST，使用稳定 eventId 和 deliveryVersion=1。最多 3 次尝试，重试间隔 1 秒、3 秒，单次请求仍为 8 秒超时；整个投递有 60 秒期限。只重试网络/超时、408/429/5xx 或缺少有效确认等可重试情况。
- **旧服务端或探测失败**：继续原来的 no-cors 单次发送，不因为看不到结果就盲目重复 POST。状态明确显示“已提交（无法确认）”或发送失败，不再声称已确认送达。
- 明确离线时先等待恢复，不先消耗一次 POST。账号/会话/轮次变化会取消后续尝试。
- 相同事件的所有重试复用相同 ID 与正文。不同页面实例拥有独立随机前缀，避免刷新或不同标签页的 generation 从 1 开始时碰撞。

后端配套实现仅影响公开通知入口，不改账号保险库、JWT、Cookie、密码或主密钥。去重为**单进程内存、有界、最多 4096 条/最长 10 分钟**，满额淘汰而不是拒绝；重启、淘汰或多实例间不保证 exactly-once。

## 诊断与隐私

探针活动记录会显示等待上下文、等待网络、检查服务能力、发送、重试、服务器已接收、兼容未确认、失败或跳过原因。

页面主环境只读诊断入口：`window.__ARENA_USERSCRIPT__.completionNotifications.status()`；其中 delivery 还可查看最近的 Thinking Stop 投递。字段仅含阶段、固定原因码、generation、尝试次数、模式和 HTTP 状态，不包含账号 ID、Cookie、密钥或会话正文。

“服务器已接收”只确认通知 HTTP 接口接受了该事件，**不是 Socket.IO 设备或 Telegram 的收件回执**。下游仍受在线状态、Telegram 队列/限流等影响。

## 交付与验收

先更新主脚本与配套助手到 .9 并刷新 Arena。仅更新脚本就可修复完成漏采样、延迟 UUID/账号问题；服务端尚未更新时会安全保持兼容发送。部署新版后端并放行 capabilities 子路径后，自动启用带确认、有界重试和进程内去重。

本次验证只使用模拟页面/传输和后端纯逻辑测试，不操作真实会话、不触发实际停止、不发送真实通知。不自动部署或重启后端。原模型命名、抽卡拖动及账号切换 2.0.5 修复保持。
