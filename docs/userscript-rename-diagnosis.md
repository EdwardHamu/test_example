# 抽卡命中后未重命名：诊断报告

> 后续已修复并部署 2026.09.24.5，见 userscript-rename-fix.md。下文保留 2026.09.24.4 的历史诊断；诊断测试现已更新为修复回归测试。

日期：2026-09-24。检查版本：user.js 2026.09.24.4。
任务原文：user.js中抽卡匹配到对应模型时, 重命名会话的功能没有成功触发, 检查原因。

## 结论与证据范围

自动命名代码已在部署的 user.js 中，且抽卡正常主/次目标路径已经接入 consider；不是遗漏打包。新增测试直接确认部署文件含本次检查的原始 CandidateBridge 和命名模块。

已通过真实桥接实现配合模拟 DOM 复现两种失败路径，并确认失败后本页去重会阻止再次尝试。因此“没有触发”也可能实际上是已触发但 UI 操作失败。本次没有连接用户实际登录页面或获取那次失败状态，不能将其中某一种断言为该次现场故障的唯一原因。

## 1. 菜单打开事件不兼容（条件性复现）

- tools/userscript-hit-rename.js:29 调用 renameMenuClick。
- assets/CandidateBridge.js:77–81 中 renameMenuClick 仅调用 button.click()；同桥的 renameMenu 则发出 pointerdown。
- 若页面菜单依靠 pointerdown 展开，单独 click 不会展开。重命名器随后轮询约 6 秒，报“等待重命名控件超时”。
- 测试用同一个真实 CandidateBridge 在 pointerdown-only 模拟菜单上验证：click 不打开、pointerdown 打开；当前自动命名流程确实超时失败。
- 尚未核验现网这一个菜单所用事件，不能仅凭此模拟断言网站一定使用 pointerdown。

## 2. 展开侧栏后的固定 250ms 等待过短（确定存在的时序缺陷）

- tools/userscript-hit-rename.js:29 展开侧栏后只等待一次 250ms，立即点击菜单。
- assets/CandidateBridge.js:16–24 要求当前会话链接已经可见且唯一，并且祖先范围内有可见的 More options 按钮。
- 渲染、动画或会话列表加载超过 250ms 时，会直接报“当前对话在侧栏中不可见”或“未找到当前对话菜单”。不会等待侧栏真正就绪。
- 新增测试复现：侧栏晚出现时立即失败，之后侧栏就绪也不会自动重试。

## 3. 失败去重导致一次短暂故障变为本页永久跳过（已确认）

- tools/userscript-hit-rename.js:48–50 在 execute 成功之前就 seen.add(key)。
- catch:38 仅记录 failed，finally:39 只清理 active；不会移除 seen。
- 此后 consider 对同账号、同会话、同模型返回 false。原抽卡循环仍可进入主目标 matched（停止）或次目标冷却流程，所以面板出现“命中”不证明名称保存成功。
- 序号已经预留，存储记录仍是 pending。刷新可清除内存 seen，但不会自动恢复抽卡或自动重命名；仍需一次新的、合法的命中触发。不能建议刷新后必然修复。

## 其他需要现场排除的门槛

- accounts.canOperate() 为 false（未确认登录、身份校验失败、Account Switch 要求刷新）时，命名会被拒绝。
- 模型所属 URL、当前会话 URL 与 generation 对齐失败时，命名钩子不会触发。
- 已有用户菜单/弹窗、页面阻塞、当前会话不在侧栏可见范围、非唯一按钮等都会安全拒绝。
- 当前重命名窗口识别依赖英文 Rename chat 或对应中文前缀；页面文案改变也可能导致识别失败。本次未验证现网文案变化。

## 如何确认用户这一次故障

在故障页先不要刷新，通过 Arena 工具 → 自动命名状态读取结果；也可仅执行只读查询：

```js
window.__ARENA_USERSCRIPT__?.hitRename?.status()
```

- failed + “等待重命名控件超时”：需结合菜单是否展开区分菜单事件、对话框识别或保存后标题更新超时；仅错误文本不能判断具体步骤。
- failed + “当前对话在侧栏中不可见”：优先检查侧栏渲染等待/当前会话是否在列表。
- failed + 账号改变/未确认：检查账号状态，不应绕过安全门槛。
- idle / 未加载：检查是否安装新版本及是否经过触发门槛。
- done / already-done：再检查是否后续被页面自动标题或用户操作覆盖，勿盲目重复分配序号。

不需要提供 Cookie、登录 Token 或消息内容。

## 后续修复建议

1. 用有界等待检测唯一会话菜单就绪，替换固定 250ms 假定；仍在每次动作前检查账号/URL。
2. 菜单尝试后先验证展开状态，必要时使用 pointerdown 路径，避免连续发送两类事件导致开后又关。
3. 为失败记录增加阶段（打开侧栏、打开菜单、填入、保存、标题核验），并提供明确的用户发起重试；沿用 pending 的编号，不移除安全检查，不无限自动点击。
4. 把结果/失败原因展示在抽卡面板，避免“命中”与“命名成功”混淆。
